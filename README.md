# Перевірка бізнес-результату квіза реєстрації

Частина B тестового завдання. Один тест проходить квіз до кінця і перевіряє, що в системі
з'явився користувач і пробний урок. Гілка під тестом - **13+** років юзеру.

## Запуск

```bash
npm run setup     # залежності + Chrome
npm test          # прогін проти stage
npm run test:ui   # UI mode
npm run report    # HTML-звіт
```

Інший env - `BASE_URL=https://... npm test`.

## Ідея

Тест ніколи не питає «на якому я кроці». Він питає «які елементи є на екрані» - модалка, поле телефону, текстове поле, опції, одинока кнопка «далі», календар - і відповідає відповідно. Тому зміна порядку, кількості чи текстів кроків його не ламає.

Усе, що має справді триматися, перевіряється через API вже після проходу: користувач існує,
відповіді квіза збереглися, урок є і він у майбутньому.

## Як працює сценарій (покроково)

**1. Фікстури** Перед стартом тесту Playwright створює `pageManager` і `apiManager` і віддає їх в аргументах. Тому в тілі тесту немає жодного `new` - усі page objects і API-клієнти вже зібрані.

**2. Вхід у воронку** Тест відкриває стартову сторінку і чекає, поки з'явиться перша кнопка з варіантом відповіді. Далі тисне опцію віку 13+ і окремо перевіряє, що екран справді змінився - якщо клік нікуди не привів, тест падає одразу з назвою опції.

**3. Відбиток екрана** Раннер не знає, на якому кроці він перебуває, тому знімає «відбиток» (signature) - шлях в URL плюс тексти всіх видимих кнопок. Квіз це SPA, адреса часто не міняється, тому самого URL було б замало. Перед кожною відповіддю раннер чекає, поки два заміри поспіль дадуть однаковий відбиток, - це і означає, що екран домалювався.

**4. Розпізнати екран і відповісти** Раннер по черзі перевіряє, що перед ним: модалка, поле телефону, текстові поля, кнопки-опції чи кнопка «Далі». Перший збіг визначає дію - закрити модалку, ввести згенерований номер, вписати ім'я або email, вибрати варіант із `preferredAnswers`.

**5. Дочекатися переходу.** Після відповіді раннер знову звіряє відбиток зі знятим до кліку. Поки URL лишається всередині частини URL `/app/sign-up/` - цикл повторюється з наступним екраном.

**6. Календар.** Якщо на екрані з'явилися кнопки з часом - це фініш. Раннер перебирає дні, тисне перший доступний слот, підтверджує бронювання і повертає фінал `trial-booked`. Вихід за межі `/app/sign-up/` без календаря дає другий валідний фінал - `request-submitted`.

**7. Запобіжник.** Цикл обмежений 40 екранами. Це не оцінка довжини воронки, а захист від нескінченного циклу: якщо ліміт вичерпано, тест падає з явною помилкою, а не мовчки впирається в загальний таймаут.

**8. Перевірки через API.** Отримавши результат проходу, тест іде в API під сесією, яку створила сама воронка. Перевіряє, що користувач існує і відповіді квіза збереглися, а далі - урок у майбутньому для `trial-booked` або порожній список для `request-submitted`.

## Модулі

**`tests/quiz-business-result.spec.ts`** - сам тест. Заходить у воронку, обирає вік учня 13+, віддає прохід раннеру і потім робить усі перевірки через API. Тут немає жодного селектора.

**`pages/QuizPage.ts`** - раннер, який проходить воронку наосліп. Кожен цикл: дочекатися, поки екран перестане мінятися → визначити тип екрана → відповісти → дочекатися переходу. Повертає результат проходу: який фінал (`trial-booked` або `request-submitted`) і який телефон згенеровано.

**`selectors/quiz.selectors.ts`** - усі локатори. У квізі немає `data-testid`, а класи захешовані, тому локатори структурні: роль елемента, тип інпута, видимість, наявність тексту. Єдине місце, де в код протікає копірайт, - `CTA_LABEL`, список підписів кнопок, які рухають воронку далі.

**`data/quiz.data.ts`** - вхідні дані. `TEEN_FUNNEL` - точка входу і опція віку; `TEEN_PROFILE` - юзер: ім'я, домен пошти і `preferredAnswers`. Останнє - один патерн (`13-15`), який раннер обирає, якщо екран його раптом пропонує; без нього продукт відправляє на ручний коллбек замість бронювання.

**`utils/fixtures.ts`** - розширює базовий `test` двома фікстурами: `pageManager` і `apiManager`. Тести імпортують `test`/`expect` звідси і отримують обидва менеджери в аргументах, тому в самому тесті немає жодного `new`.

**`utils/pageManager.ts`** - доступ до page objects. Створює інстанс при першому звертанні до getter, нові інстанси класів виду `new QuizPage(...)` ніколи не ініціалізуються в тесті.

**`utils/apiManager.ts`** - те саме для API-клієнтів (аналогія page manager'а). Створюється разом із фікстурою, ще до того, як воронка когось зареєструє.

**`utils/api.ts`** - модуль для двох ендпоінтів перевірки: користувач (`/api/v1/users?me=true`) і його майбутні уроки (`/api/v1/lessons`). Токен бере з сесії, яку сама воронка створює під час реєстрації - сервісного акаунта немає, це єдиний доступний credential.

**`utils/dataGenerator.ts`** - генерує тестові дані на кожен прогін: унікальний телефон і унікальний email. Номер будується з маски, яку рендерить сам застосунок — країну не захардкоджено навмисно, бо застосунок визначає її з IP, тож у CI маска буде інша.

**`playwright.config.ts`** - один проєкт `chrome`, `retries: 0`, `workers: 1`. Zero retries не випадково: завершений прохід створює реального користувача і реальну бронь, тому retry забронював би другий урок.

## Припущення

- **Прогін має побічні ефекти.** Кожен завершений прохід створює реального користувача і бронює реальний урок на stage. Прибирання за собою немає - потрібен test data clean up або пул тестових даних.
- **Телефон має бути унікальним.** Повторний номер відхиляється, і воронка мовчки викидає на `/uk/app/login`. Тому номер генерується заново на кожен test run.
- **Фіналів два.** З тими самими відповідями воронка іноді доходить до календаря, а іноді завершується на `/uk/app/request-gotten` («адміністратор зв'яжеться з вами») - схоже, коли в тестового викладача не лишилось вільних слотів. Обидва вважаються валідними й перевіряються по-різному; фактичний фінал пишеться в анотацію тесту.

## Що зробив би далі (за наявності часу)

- **Cleanup.** Teardown, який видаляє створеного юзера і скасовує бронь через API. Зараз кожен прогін лишає реальні дані на stage.
- **Решта гілок воронки.** Залежно від відповідей квіз розгалужується на десяток різних проходів, а тест іде лише одним із них. Раннер не знає, якою гілкою він рухається, тому щоб покрити інші, достатньо описати їхні вхідні дані в `data/quiz.data.ts` і прогнати той самий тест по цьому списку.
- **CI.** GitHub Actions на кожен PR, з публікацією HTML-звіту і збереженням trace для failed прогонів.
- **`data-testid` від розробників.** З testid на ключових кнопках локатори перестануть залежати від текстів.
- **Швидше падіння на заклиненому екрані.** Зараз результат очікування переходу не перевіряється, тому застряглий екран мовчки крутить 20-секундні цикли до загального таймауту замість явної помилки.
- **Глибші API-перевірки.** Наразі перевіряється, що `funnel-data` не порожній. Варто звіряти конкретні відповіді квіза з тими, що реально відправив раннер.
